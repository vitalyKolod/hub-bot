## SUPPORT FLOW

Помощь или `/support` → категория → причина → при необходимости один экран контекста
→ сообщение. Первое сообщение вызывает существующий `createSupportTicketForUser`.
Открытый тикет переиспользуется. Новый контекст сохраняется в metadata; при повторном
входе в открытый тикет в его топик добавляется сообщение с обновлённым контекстом,
поэтому прежняя информация остаётся в истории. Следующие сообщения используют старый relay.

«Назад» возвращает на предыдущий экран. Отсутствие платежей, подписок или команд
не блокирует обращение. Один подходящий платёж выбирается автоматически. Большие
списки разбиты на страницы по восемь вариантов. Выбор не создаёт тикет заранее.

## CATEGORIES

Ровно шесть категорий: Оплата; Подписка / доступ; Команда / волонтёры;
ProPresenter; Работа HUB; Другое. «Другое» сразу открывает ввод сообщения.

## SUBCATEGORIES

- Оплата: отклонена, не получается оплатить, чек долго на проверке, стоимость,
  оплачено без доступа, другое.
- Подписка / доступ: нет доступа, нет приглашения, данные входа, продление,
  срок подписки, другое.
- Команда: добавить волонтёра, не получается вступить, нет приглашения,
  проблема с участником, подписка команды, другое. Команда выбирается до причины.
- ProPresenter: поток, данные входа, заявка, чат / приглашение, продление, другое.
- HUB: работа бота, команда, уведомления, интерфейс, другое.

## CONTEXT METADATA

`SupportTicket.metadata` содержит необязательные поля:
`category`, `subcategory`, `source`, `paymentId`, `teamId`, `productIds`.
Подписки выбираются из существующих team.subscriptions, включая несколько продуктов.
Цены/названия продуктов берутся из PRODUCTS; исторические платежи имеют fallback.
Для вопроса о стоимости можно выбрать продукт либо продолжить без выбора.
Дополнительные модели подписок, CRM или ProPresenter не создавались.
Автоматическая привязка stream/request ID не добавлялась: это необязательная часть задания.

Карточка нового тикета показывает тему, причину, пользователя и выбранный контекст.
Для платежа отображаются продукт, сумма, валюта, статус и причина отклонения.
Существующие кнопки профиля, команды, Telegram-профиля и close/reopen сохранены.
Отдельная кнопка перехода к admin payment card не добавлялась.

## PAYMENT REJECTION SHORTCUT

Единственное изменение в доставке уведомления об отклонении — callback кнопки:
`s2:reject:<paymentId>`. Текст уведомления и адресат не менялись.
Обработчик проверяет доступ: сам плательщик либо текущий владелец команды,
которому существующий код отправляет уведомление.

Кнопка сразу показывает «ВОПРОС ПО ОПЛАТЕ», без выбора категории или платежа.
Metadata: `source=payment_rejection`, `category=payment`,
`subcategory=payment_rejected`, `paymentId=<id>`.

## PAYMENT/SUPPORT ISOLATION

При сознательном входе в поддержку снимается только `userActive` существующих
conversations пользователя, по тому же принципу, который уже применяет активация
conversation. Ни status, ни сами conversations не закрываются и не удаляются.
Ожидание загрузки чека снимается при явном переходе в Support, чтобы фото вопроса
не было принято за чек. Сам платёж и его бизнес-статус не меняются.

Во время выбора раннее сообщение не пересылается. После выбора остаются прежние
обработчики и их последовательные return: один message имеет одно назначение.
Позднейшая активация Payment администратором сохраняет существующий приоритет
resolver. Conversation service, его модели и admin-команды не редактировались.
Registration / ProPresenter Requests / Stream Confirmations не получили communication mode.

Existing Support relay was reused, not rewritten.
Existing Payment conversation was not changed.
Payment and Support messages cannot be delivered to both contexts simultaneously.
Последнее утверждение проверено автоматическими тестами маршрутизации с mock API;
реальный Telegram end-to-end не запускался.

## MANUAL TEST

Нужны тестовый пользователь, support group и администратор с существующими правами.
Реальный Telegram-клиент в этой задаче не запускался.

1. **GENERAL SUPPORT:** Главное меню → Помощь → Оплата → Чек долго на проверке.
   При двух pending/processing платежах выбрать один; при одном он выбирается сам.
   Написать текст, затем отправить фото/голосовое. Проверить тему, причину, продукт,
   сумму и статус в support group. Ответить из топика текстом и файлом; проверить
   доставку пользователю и реакции. На шагах выбора проверить «Назад».
2. **SUBSCRIPTION:** Помощь → Подписка / доступ → Нет доступа → выбрать две подписки
   → Продолжить → написать. Карточка должна содержать оба продукта. Повторить без
   подписок: обращение должно быть доступно без выбора.
3. **TEAM:** Помощь → Команда / волонтёры → выбрать команду → Не пришло приглашение
   → написать. Проверить название команды и сохранённые admin-кнопки. Повторить
   без команд и со старой/удалённой командой: отсутствие контекста не вызывает падения.
4. **REJECTED PAYMENT:** Отклонить платёж с причиной → пользователь нажимает
   «Написать в поддержку». Должен сразу появиться вопрос по оплате. После сообщения
   support group получает тему, причину, пользователя, продукт, сумму, статус и
   rejection reason. Payment conversation и статус платежа остаются без изменений.
5. **ISOLATION:** Открыть Payment conversation и Support для одного пользователя.
   Явно войти в Support и написать: одна копия только в support group. Затем
   администратор активирует Payment и пользователь отвечает: одна копия только
   в payment context. Проверить, что оба контекста сохранены и нет дубликатов.
6. **LIFECYCLE:** В support group завершить и возобновить обращение, проверить
   сохранение кнопок профиля/команды/Telegram-профиля. Проверить существующий
   auto-close после периода неактивности. Повторно войти в Support при открытом
   тикете с другой темой: новый топик не создаётся, обновление контекста видно в истории.
